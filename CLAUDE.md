# CLAUDE.md

## Project
Outfit recommender chatbot. The user uploads photos of their own clothes; the system tags, embeds and stores them, then a multi-agent system recommends outfits based on occasion, weather (temp, rain, wind), color theory and fit preferences.

Purpose: resume demo showing agentic AI, multi-agent orchestration, vector search, local model inference, and a Claude Code workflow. Code quality and clarity matter more than feature count.

## Current focus: all phases and planned features done
Phases 1-7 are complete (ingestion, tools, agents, eval, API, UI); each has an explainer in `docs/phases/` (history, results and design choices live there, not here). The agent design is `docs/agentic-architecture.md` (router -> intake (interrupt to ask) -> orchestrate -> stylist -> critic (max 1 revision) -> respond; `refine` is the only ReAct loop, max 4 tool calls): update it if the design changes. Eval baseline: final prompts `3a5c446a` 63/63 over 3 runs (`docs/phases/phase-5-evaluation.md`); prompts changed since (accessories, socks), eval not re-run.

Built after the phases, planned and tracked in `docs/features_to_add.md` (keep its decisions and step statuses up to date as they are discussed and built): user profile, shopping assistant, accessories, trip packing list (§4, `docs/phases/packing.md`, live-checked 2026-10-25). Wear feedback (§5, `docs/phases/wear-feedback.md`, live-checked 2026-10-27). Docker (CPU-only image) was deferred by the user: don't start it unless asked. Optional later: Docker, a persistent conversation store, harder eval scenarios. One-command start: `scripts/run_app.py` (`outfit/launcher.py`). The end-user guide is `docs/user-guide.md` (update it when a page, command or limit changes).

## Stack
- Python 3.11+, all code in Python. Environment: Python 3.12, a shared venv (path in `CLAUDE.local.md`)
- **All local inference runs on CPU.** Never install, upgrade or replace `torch` (pinned at 2.7.0+cu118); dry-run (`pip install --dry-run`) any new dependency that might pull torch.
- DeepSeek API — model `deepseek-flash` (V4.1-Flash, image input) for vision tagging and agents. DeepSeek has no Python SDK; call it with the `openai` package pointed at `https://api.deepseek.com` (OpenAI-compatible). Nothing is sent to OpenAI.
- Qdrant in local mode: `QdrantClient(path="./qdrant_data")`
- `open_clip_torch` (ViT-B-32, `laion2b_s34b_b79k` weights, 512-dim) for image and text embeddings, run locally with `device="cpu"`
- `rembg` for clothing segmentation via open-source ONNX models on CPU `onnxruntime` (no torch): `u2net_cloth_seg` for worn clothes, `birefnet-general` for flat-lay (won a 5-model bake-off on real bed photos, ~26 s/photo on CPU; see `config.py`); model is configurable. Only one large ONNX model fits in RAM next to the rest, so compare models one at a time. `Pillow` for image handling
- `scikit-learn` (k-means) + `scikit-image` (RGB→LAB) for color
- Pydantic v2 for all schemas and structured LLM output
- LangGraph (1.2.x, already in the venv) for agent orchestration only; LLM calls go through the same DeepSeek client as the tagger, not LangChain model wrappers
- FastAPI + uvicorn (API, `[api]` extra), Streamlit (UI, `[ui]` extra); Docker deferred
- Tests: pytest

## ClothingItem schema (source of truth)
- `id`: UUID
- `image_path`: path to cleaned PNG
- `category`: enum — top, bottom, one_piece, outerwear, footwear, ethnic_top, ethnic_bottom, accessory
- `subtype`: free text (e.g. "kurta", "jeans", "shorts", "blazer")
- `primary_color_name`: str; `primary_color_lab`: tuple[float, float, float]
- `secondary_colors`: list[str]
- `pattern`: enum — solid, striped, checked, floral, printed, other
- `fabric`: str (best guess: cotton, denim, linen, wool, silk, synthetic…)
- `length`: enum — cropped, short, knee, midi, full
- `fit`: enum — slim, regular, relaxed, oversized
- `formality`: int 1–5 (1 = gym, 5 = black tie / wedding)
- `warmth`: int 1–5 (1 = very light, 5 = heavy winter)
- `flowy`: bool (matters for wind)
- `occasions`: list of enum — casual, office, formal, sports, party, indian_festive, wedding, travel, lounge
- `created_at`: datetime

Qdrant collection `wardrobe`: named vector `image` (512, cosine); point id = `ClothingItem.id`; payload = all other fields (JSON mode). Create payload indexes on `category`, `formality`, `warmth`, `occasions`, `flowy` (no effect in local mode, kept for a Qdrant server). Item ids come from `schemas.stable_item_id(photo_bytes, region)` (uuid5), so re-ingesting a photo updates its items instead of duplicating them. Only one process may open the local `qdrant_data/` path.

## Conventions
- Type hints everywhere; small pure functions; no global mutable state except the cached CLIP model and the cached rembg sessions (`background.get_session`, one per model name).
- Flat masks go through `remove_thin_parts` (`THIN_PART_RATIO`, opening + stay near the thick body) to trim hanger hooks; worn masks don't (straps). Tune it on real photos, not guesses.
- Segmentation has two modes (`SegMode`): `flat` (garment alone → one `whole` cutout) and `worn` (on a person → `upper`/`lower` cutouts, or one `full` for a one-piece). One photo can yield several garments, so `ingest_image()` returns `list[ClothingItem]`. The region is only a hint; the tagger decides `category`.
- LLM calls use DeepSeek JSON mode (`response_format={"type": "json_object"}`), which guarantees JSON but not a schema, so the JSON schema is spelled out in the system prompt (`{{schema}}` in `tagger.md`) and Pydantic validates. Retry once on invalid, empty or truncated output (feeding back the error), then raise; `content_filter` is not retried.
- The tagger sends DeepSeek only the garment cutout flattened onto grey (base64 PNG data URL), never the original photo (cutouts keep the old background under transparent pixels, so always flatten).
- Ingestion tags and embeds every garment in a photo before writing, so a failed photo leaves the store untouched; re-ingesting keeps the original `created_at`. Shopping candidates go through the same `describe_photo` into `Settings.candidates_dir` (gitignored) and are stored only on "add", reusing their tags and vector.
- Embeddings: cutouts are composited onto neutral grey (128,128,128) before CLIP; all vectors are L2-normalized. Search = payload filters (`ItemFilter`) for hard constraints + vector similarity for ranking. Text queries use the caption template `"a photo of {query}"` (chosen by margin to the runner-up on the real wardrobe).
- Weather: Open-Meteo (no key) over stdlib `urllib` (`http_get_json`, retries 5xx/network errors; tests inject a fake `fetch`); a null rain chance (far-ahead forecasts) is read off the hour's rainfall (`WET_HOUR_MM`). Times are naive local time at the place (`tzdata` on Windows). Rules in `advise()` are named threshold constants: temperature uses the *minimum feels-like* over the outing, minus ride chill on bike/two-wheeler below 25°C; riding always avoids flowy; a car with < 0.5 h outdoors is "not exposed", so rain/wind/UV only add notes and outerwear becomes optional. `WeatherAdvice.item_filter()` gives the hard filters (warmth, flowy) for base garments; fabrics, colors and outerwear are for outfit ranking.
- Color harmony: lightness and chroma from LAB, but hue on the RYB artist's wheel (LAB → RGB → HSV → RYB), because styling complements (red–green, blue–orange, yellow–purple) are only ~96–114° apart as LAB hue angles. Neutral-ness comes from the color *name* (`NEUTRAL_WORDS`) or denim fabric first, chroma < 6 second: real photos are so desaturated (wardrobe max C≈19; pastels C≈9–12) that a chroma threshold would call pastels neutral. Hue counts only above chroma 10, fully at 30; below that two colors score as "soft colors". Rules are named constants; scores are 0..1 and always carry a reason the agents can quote.
- Outfits: base = top/ethnic_top + bottom/ethnic_bottom, or a one_piece; footwear and outerwear are add-ons. Hard rules (occasion, formality range — default from `OCCASION_FORMALITY` — and weather warmth/flowy) apply to base garments only; a base tagged for a near occasion (`NEAR_OCCASIONS`) passes if its formality fits (−`NEAR_OCCASION` fit), and bottoms may be `BOTTOM_WARMTH_SLACK` warmer than the range (−`WARM_BOTTOM`), because the tagger tags few occasions and rates nearly all full-length bottoms warmth 3; at formal/wedding a plain bottom may be `BOTTOM_FORMALITY_SLACK` below the range (`dressy_bottom_slack`, −`LESS_DRESSY_BOTTOM`); lounge bottoms need their own tag (`OWN_TAG_ONLY`) and `AT_HOME` occasions get no shoes or accessories; when no base fits, the gap (`NO_BASE`) names the closest misses (`closest_misses`); add-ons are scored and only added at fit ≥ `MIN_ADDON_FIT`, otherwise reported as a gap. Score = 0.5 color harmony + 0.5 fit (piece fit minus pattern-clash / formality-spread penalties) + taste, clamped 0..1. Taste (`taste()`, from the profile via `OutfitRequest.colors_liked/colors_avoided/fit_tops/fit_bottoms`, filled by orchestrate) is uncapped because piece fit is capped at 1.0 and nearly every piece sits there: per piece +`LIKED_COLOR`, −`AVOIDED_COLOR` (never a ban), +`PREFERRED_FIT` (tops/bottoms only); colors match whole words of `primary_color_name` only (`color_is`); each adjustment adds a reason. `must_include` items skip hard rules but lose `BROKEN_RULE` fit per break and surface as warnings. Variety: a base garment appears in at most `MAX_REPEATS` results; shoes/outerwear may repeat. Pure functions over `list[ClothingItem]`; the store is only read by the CLI.
- Agents: LLM nodes get the DeepSeek client and settings via `functools.partial` in `build_graph`; structured calls go through `agents.llm.chat_json` (model `agent_model`). Never call `interrupt()` in a node that also calls the LLM: on resume LangGraph re-runs the whole interrupted node, so asking lives in its own `ask` node. Code owns defaults and validation (`merge_slots` drops invalid values field by field; only `start="now"` is defaulted; outdoor time is always asked); every default or give-up goes into `assumptions`. New types stored in `ChatState` must be added to `graph.STATE_TYPES` (checkpoint msgpack allowlist). Non-LLM dependencies (store, weather `fetch`, item resolver) come in through `orchestrate.Context`; tests use `tests.fakes.fake_context(items, resolve=, fetch=)` and `stylist_reply()`. The stylist only sees `stylist.facts(state)` (plan, weather, notes, assumptions), never the wardrobe or photos; anything that should reach the user must be in those facts. Item references ("my lavender skirt") resolve by tags first (`tools/match.py`: the reference's head noun must be one of the item's garment words — subtype or category — then most words matched wins; plural "s" dropped, hyphenated tags match their parts), CLIP only breaks ties or, when no tag matches, needs score ≥ `MIN_MATCH_SCORE` (0.24); CLIP alone mis-ranked real items (lavender skirt below beige trousers). Every resolution is reported in `assumptions`. A failed forecast is an assumption (`orchestrate.WEATHER_FAILED`), never a gap (gaps are shown as "missing from your wardrobe"); the critic's code checks require it to be passed on (`critic.ASSUMPTION_TOPICS`). Intake corrects misspelt cities, maps "casual party" to formality [2, 3] and a day without a time to the occasion's time (dinner tomorrow → `tomorrow 19:00`). Planning with `skip_weather` always leaves a weather assumption (`orchestrate.NO_WEATHER` unless intake's give-up note is there), so the reply says the weather was not checked. `chat_json(..., max_tokens=)` bounds reasoning tokens too: DeepSeek counts thinking against `max_tokens`, and the critic rubric gets `critic_max_tokens` (4096) because it alone hit 2048 in the eval. Refine's `search_wardrobe` uses the same order (tag matches first, never `weak`). The critic's code checks rely on the stylist saying "your" only for plan pieces ("a ..." for suggestions); keep that rule in `stylist.md`. Only the first draft goes back for a revision (and only it gets the LLM rubric); after it the critic makes the draft safe instead: invented piece → no draft (template), left-out notes/gaps → appended. Graph tests queue `critic_reply()` after every clean `stylist_reply()`. Every new (non-resume) message starts at the router, so graph tests queue `router_reply(intent)` first; refine steps use `tool_call_reply((name, args), ...)` and `Context.search` is `tests.fakes.FakeSearch` (word overlap, no CLIP). Refine tools only change state (`slots`, `plan`, `found`, assumptions); the model's own closing text is logged and dropped, so anything the user should hear must reach `stylist.facts`. A `new` intent clears the request and keeps the old one as `previous_slots` (intake may use it only for explicit back-references). Respond resets all per-turn fields (`found`, `react`, `tool_calls`, critic counters), so anything inspecting a turn (recordings, evals) must use `recording.run_turn`, which streams per-node updates, not the final state. Recordings shorten garments to id prefix + name and tag each turn with `prompts_version()` (hash of `prompts/*.md`) to compare before/after a prompt change. Eval scenarios: every `Expect` field is optional and unset means unchecked; the schema forbids unknown keys, slots and tools, so typos fail at load time. Expectations check outcomes (intent, slots, tools called, plan contents, words in the reply), never exact reply text; `start` compares by `parse_start` at the file's fixed `now`. The clock is `Context.now` (None = real time): `build_graph` passes it to intake, `tools_node` and orchestrate read it, so never call `datetime.now()`/`local_now()` in a node without falling back to it. Evals use `graph.clip_context(store, settings, fetch, now)` (real CLIP over the snapshot) — the same constructor `live_context` uses. Each scenario gets a fresh graph, thread and in-memory store, so scenarios run in parallel. Turn metrics come from the recording (`runner.turn_metrics`).
- API (Phase 6): `create_app(services)`; one `Services` per process owns the only Qdrant client, shared by ingestion and chat. Endpoints are sync `def` (blocking store/CLIP/graph run in FastAPI's thread pool); domain errors map to status codes only in `api/errors.py`. Uploads trust the bytes, not the filename or content type: `photo_suffix` decodes the whole image (`load()`, since `verify()` passes truncated JPEGs) and enforces `max_upload_mb`; `photo_path` keeps only a sanitized stem inside `raw_dir`. Ingestion and re-tagging hold `Services.ingest_lock`; a failed ingest removes the photo it just saved. Chat: conversations live in `Services.checkpointer` (in memory, lost on restart; an unknown `thread_id` is 404); each turn compiles `Services.graph(RecordingClient(client))` so its record holds only its own LLM calls; whether to resume comes from `get_state(config).next`, never from the client; a per-thread lock refuses a second concurrent message (409). The open question is in `state.interrupts`, not `messages` (ask adds it on resume). `run_turn` returns this turn's raw `plan` and `shown` items (respond resets `found`, the router clears `plan`). `record_chats` writes turns like `chat.py --record`. API tests: `tests.fakes.fake_services(items, client=, pipeline=, settings=, fetch=)` + `TestClient`; upload tests reuse `tests.test_pipeline.make_pipeline` (fake rembg + CLIP) with `pipeline.store = services.store`.
- UI (Phase 7): Streamlit talks only to the API through `ui/client.OutfitAPI`; it must never import `outfit.api`, `outfit.agents`, `outfit.ingestion`, torch, Qdrant, openai or fastapi (a subprocess test checks the import list); `outfit.schemas` (enums) is fine. Client models mirror the API's responses and are tested by parsing real responses from `create_app(fake_services(...))` via `OutfitAPI(http=TestClient(...))`. Pages are `render(api)` functions; tests run them headless with `AppTest.from_function` (or `from_file("src/outfit/ui/app.py")`), putting the API client in `at.session_state["api"]`; give test items real cutout files or pictures fall back to "(no picture)". Use `width="stretch"`, not the deprecated `use_container_width`. AppTest can't drive `st.file_uploader`, so uploads are tested at the API/client level; form submit buttons are found by `button.proto.form_id`, widgets by key (`f"{field}-{item.id}"`).
- Profile: one per install in `Settings.profile_path` (gitignored), every field optional; a field is added only if something uses it. `ProfileStore(path)` writes a temp file and swaps it in; `ProfileStore()` stays in memory, which is what `Services` and `fake_services` default to, so tests never touch `data/`. A saved place's `dress_code` overrides the occasion's formality (`DRESS_CODE_FORMALITY`); the chat must confirm a saved trip before using it. Agents read the profile through `Context.profile` (a loader called every turn, default `Profile` = empty, so evals and tests without one are unchanged; `fake_context(profile=)`, `fake_services` wires its in-memory store). Intake: the model returns `place` (a saved name; unknown names are dropped by `known_place`) and `use_saved_trip` (the answer to "same as usual?"); code adopts the place's occasion and dress code at once (`adopt_place`, unless a formality is already known), puts the pseudo-slot `SAVED_TRIP` first in `missing` while the trip is unconfirmed (`with_trip_question`; it covers the slots it would fill), fills only still-unknown trip slots on yes (`use_saved_trip`), assumes the trip when giving up, and defaults a missing city to the home city (`home_city`); every one is an assumption. `saved_places` is left out of the extraction payload when there are none. Eval scenarios may carry a `profile` table (tag `profile`), and `missing` accepts `saved_trip`. The UI can't import `outfit.profile` (it loads Qdrant via `outfit.tools`), so `ui/client.py` mirrors its enums as `Literal`s; `tests/test_ui_profile_page.py` checks they match. Photo: `ProfileStore.save_photo` keeps only `reencode()`d JPEG (upright via EXIF orientation, ≤1024 px, no EXIF); `analyse_colouring` sends another re-encode (≤768 px) to `tagger_model` via `chat_json(model=)`, only from `POST /profile/analyse`; the prompt (`colouring.md`) judges undertone/depth, hair, eyes, contrast only and never ethnicity, age, gender, body or looks; `face_visible: false` -> `NoFaceVisible` (422), nothing saved. Deleting the photo keeps `Profile.colouring`. Taste adds `SUITS_COLORING`/−`GO_EASY_COLOR` from `colouring.suits/go_easy` (`OutfitRequest.colors_suit/colors_go_easy`), skipped for a piece the user's own likes/avoids already matched. AppTest drops a second submit of one form right after `st.rerun()`, and keeps elements from the run that called `st.rerun()`: run once more before asserting an element is gone. Page tests that need a check result run it through `OutfitAPI.check_item` against the fake API and put it in `session_state.shopping_check`. Place forms are keyed by the lower-cased place name, the add form by a counter (`places_added`) so it empties after each add.
- Shopping (`tools/shopping.py`, pure): situations = saved places (with dress-code formality) first, then `Profile.occasions` no place covers, else `DEFAULT_OCCASIONS`; each is checked in every `tools/climate.py` kind of the home city (Open-Meteo archive, last 365 days ending `ARCHIVE_LAG_DAYS` ago; a kind counts at ≥ `MIN_SHARE` of days; no city or a failure = all four) via `typical_advice(kind)` (a fixed daytime public-transport outing through the normal `advise()`). It compares `all_outfits` with and without the candidate (never `suggest_outfits`: its variety cap would hide counts); new outfits = distinct outfits with it scoring ≥ `GOOD_OUTFIT`, other shoes/outerwear and other situations counting once; unlocks = situations with no good outfit before; fixes = gaps closed. Look-alikes come from the caller (CLIP, same category; `DUPLICATE` 0.85 and `SIMILAR` 0.75 were calibrated on the real wardrobe: same garment re-shot 0.82-0.99, different garments ≤ 0.79; see `docs/phases/shopping-assistant.md`); a candidate whose id is already in the wardrobe is "owned" and always a skip. Verdict: no new outfit -> skip; duplicate -> skip (maybe if it unlocks/fixes); unlock, fix or ≥ `BUY_OUTFITS` -> buy; else maybe. Taste comes in as an `OutfitRequest` built from `Profile.taste_fields()` (orchestrate uses the same helper). The API check (`api/shopping.py`) describes the photo under `ingest_lock` into `candidates_dir` (a failure deletes the photo), takes look-alikes from `store.search(vector, same category)`, and gets weather kinds from `Services.climate(city, today)` (cached per city and day, `Context.fetch`, `Context.now` for today); candidate cutouts are served at `/shopping/candidates/{id}/image`, and after "add" at `/items/{id}/image`. Unlocks are grouped per situation (`group_where`: "wedding in any weather"; `unlocked` keeps the raw count); the planner's "nothing fits" gap (`outfits.NO_BASE`) is an unlock, never a fix. What to buy (`tools/staples.py`): staples are tag sets in `staples.toml` (validated `Staple` rows; colors from `COLORS`, LAB as photos measure them), never photos; each is checked via `check_candidate` with a shared `baseline()` (the slow part otherwise) in the color with most "goes with" partners (avoided/go-easy/owned-kind colors skipped, liked wins ties); picks are greedy (each pick joins the wardrobe before the next round; a staple not worth it is dropped), only "buy" verdicts, shoes/outerwear only with an unlock or fix (a new pair of shoes makes every outfit "new"), and `best_pair` tries a top + bottom when no single staple unlocks an empty situation. `ryb_hue` is `functools.cache`d. Accessories in shopping: `all_outfits`/`baseline()` never contain them, so an accessory candidate skips the with/without comparison: `accessory_effect` counts the baseline's good outfits `choose_accessories` would add it to ("new outfits") and the accessory gaps it closes (fixes); it is a buy only with a fix. `accessory_gaps(wardrobe, before, taste)` feeds `missing(before, kinds, accessories)`; never put accessory gaps into `baseline()` (any garment would then "fix" them). Accessory staples exist only for kinds with a gap (sunglasses, wool scarf, silk tie); `gain` ranks clothes before accessories at equal fixes. `climate.TYPICAL_DAY` carries a UV per kind: only hot and mild are `sunny`.
- Accessories (`tools/accessories.py`, `docs/features_to_add.md` §3): the kind (belt, tie, bag, sunglasses, hat, scarf, dupatta, watch, jewellery) comes from the subtype's last kind word, never a schema field. Socks/stockings/tights are tagged `accessory` (`tagger.md`) with no kind, so outfits ignore them (the tagger had made socks a bottom and a footwear). They are chosen after the outfit, at most one per kind, so they never change which outfits rank: `finish_plan` adds them after the outfit's pieces with the score unchanged, and `all_outfits` (shopping counts) never sees them; a requested accessory is left out of its `must_include` check and always added, with warnings for broken rules. Hard rules: belt needs a `takes_belt` bottom, tie a shirt (`is_shirt`: the word "shirt", not t-shirt/polo) and a range reaching `TIE_FORMALITY`, dupatta an ethnic piece, sunglasses/hat/scarf only when `called_for` (`WeatherAdvice.sunny`/`riding`, felt temp < `COLD_C`); flowy ones are out under `avoid_flowy`. Score = harmony with `partners` + `piece_fit` (accessories are in `ACCESSORY_SLOTS`; `OUTDOOR_ONLY` sunglasses skip occasion/formality) + leather match + taste, kept at ≥ `MIN_ADDON_FIT`. Gaps only when called for: sunglasses in strong sun, scarf in the cold, a tie at formal/wedding if the user owns ties. Accessories reach the stylist, API and UI as ordinary `pieces` (category `accessory`, last); `stylist.md` names them after the clothes, `critic.md` treats listed ones as part of the outfit, and `critic.GARMENT_NOUNS` / `GAP_TOPICS` carry the accessory words, so keep them in step with `accessories.KIND_WORDS` and `accessories.missing`.
- Wear feedback (`wear_log.py`, `tools/feedback.py`, `docs/features_to_add.md` §5): a pairing (`outfits.pairing`: top + bottom, or one-piece + shoes) takes its latest entry's rating (loved -> +`LIKED_PAIR`; not again or the colours issue -> -`DISLIKED_PAIR`; fine clears); base garments worn in the last `RECENT_DAYS` -> -`WORN_RECENTLY` each; all via `OutfitRequest.liked_pairs/disliked_pairs/recent` and `history()` (uncapped, like taste, a reason each). Too cold minus too warm >= `WARMTH_REPORTS` shifts the advice's warmth (and outerwear minimum) by one (`shifted`), only when there is advice, with `warmth_note()` as an assumption. Chat reads the log through `Context.wear_log` (default: empty; `fake_context(wear_log=)`, `fake_services` wires its in-memory `WearLogStore`); packing passes `plan_trip(history=)` and ignores recent wear; shopping doesn't use the log. Worn photos stay local (only `POST /worn/{id}/look` sends a copy; `look.md` scores the outfit, never the person): `Pipeline.worn_vectors` (no tagging) + `worn_match` (same-kind pieces; no score decides alone, the user confirms via PATCH); kept only if a garment was found.
- Packing (`tools/packing.py`; details in `docs/phases/packing.md`): confirm first: `preview_trip` (place matches via `weather.find_places`, dates, a row per slot with weather and `Source`) uses no wardrobe; `plan_trip` raises `PlaceNotConfirmed` (422) for a city without `Trip.place`; any trip or event change in the UI drops the check. Slots without forecast hours take last year's same dates (`climate.archive_hours`), always an assumption, never a gap; `indoors` slots (evenings in) get no weather and fetch nothing. `pack` is pure: greedy cover over `all_outfits` >= `GOOD_OUTFIT` by newly dressed slots per new piece, `Wears` limits per distinct day, no base on two days (`scripts/check_variety.py`), `wear_again` past them with one note; accessories via `finish_outfit`; only used pieces are packed.
- Scripts share parsers via `outfit/cli.py`; never import one script from another (`scripts/` is not a package).
- CLIP similarity means "looks alike", not "goes together" (items cut from one photo score high because they share its lighting), so outfit pairing uses color harmony and tags, not `similar_to`.
- Color is computed locally (k-means on non-transparent pixels), never trusted from the LLM alone; the LLM provides the color *name*.
- Corrections (`review.py`) touch only the tag fields (`TagResult`); id, cutout, vector, color LAB and `created_at` stay pipeline-owned. An owner's note goes to the tagger as `note=` and overrides the image. Replacing via a photo ingests the new photo first and removes the old item only after that succeeds.
- Secrets only from `.env` (`DEEPSEEK_API_KEY`; template in `.env.example`). Never hardcode or commit keys. Claude Code must not read `.env`: a PreToolUse hook (`.claude/hooks/block-env.ps1`), deny rules in `.claude/settings.json` and `.ignore` enforce this; don't work around them, and never log or print settings secrets.
- The shared venv has `pip-system-certs`, whose startup patch of `ssl.SSLContext` makes openai's HTTPS stack recurse forever. `outfit/__init__.py` undoes it (`_ssl_fix.py`) before openai is imported; keep that import first, and don't import openai/httpx2 ahead of `outfit`.
- Log with `logging`, not print.
- Keep prompts in `src/outfit/prompts/` as `.md` files, not inline strings.

## Commands
- Install: `pip install -e ".[api,ui,dev]"`, or the tested pins: `pip install -r requirements.txt && pip install -e . --no-deps` (torch is in neither; keep `requirements.txt` in step with `pyproject.toml`)
- Run everything: `python scripts/run_app.py [--port 8000] [--ui-port 8501] [--record] [--no-browser]` (Ctrl+C stops both)
- Run the UI alone: `streamlit run src/outfit/ui/app.py` (API must be running; `OUTFIT_API_URL` if not on :8000)
- Serve the API: `python scripts/serve.py [--port 8000] [--record]` (docs at `/docs`; stop `chat.py`/`review_wardrobe.py` first, one process per `qdrant_data/`)
- Tests: `pytest -q` (real-model tests: `pytest -q -m slow`)
- Ingest: `python scripts/ingest_folder.py data/wardrobe_raw --mode flat|worn`
- Review/fix items: `python scripts/review_wardrobe.py [--match dress] [--no-show]`
- Search: `python scripts/search_wardrobe.py "black dress" [--formality 3-5] [--category top]` or `--like <id prefix>`
- Pack: `python scripts/pack_trip.py --city Manali --first-day 2026-11-06 --days 4 [--event 2,party,20:00,4,0.5,car] [--place 2] [--tops 3] [--yes]`
- Chat: `python scripts/chat.py [--verbose] [--record]` (`--record` appends each turn as JSON to `data/conversations/`, gitignored)
- Outfits: `python scripts/suggest_outfits.py --occasion party [--city Pune --start 19:00 --hours-away 4 --hours-outdoors 0.5 --transport car] [--with <id>] [--like navy --avoid black --fit-tops relaxed]`
- Weather: `python scripts/check_weather.py` (asks questions) or `--city Pune --start 18:30 --hours-away 4 --hours-outdoors 1 --transport two_wheeler`
- Agent eval (real API, asks first): `python scripts/eval_agents.py [--tag refine] [--only id,id] [--repeat 3] [--yes]`; Claude Code runs it only with the user's go-ahead for that run
- Lint/format: `ruff check . && ruff format .`
